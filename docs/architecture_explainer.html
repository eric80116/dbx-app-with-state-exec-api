The problem

A machine identity in front of a governed lakehouse erases the governance

The Statement Execution API authenticates as a single service principal. Hand it directly to end users and everyone shares that one identity — Unity Catalog can no longer tell people apart, and grants, masks, and row filters stop meaning anything. What's needed is a service layer that lets each user reach the data as themselves.

The core idea

A Databricks App enables OBO and runs every query with the caller's own token. The browser UI and the public REST API share one execution engine — the same SQL, run by different people, and Unity Catalog decides what each of them sees.

Request lifecycle

Two entry points, one governed engine

Whether a request arrives from the browser or from a script, the backend resolves the caller's identity, then executes with that token. Nothing runs as a shared service principal.

Browser (UI)
  1. User signs in to the App with workspace SSO.
  2. Databricks Apps injects X-Forwarded-Access-Token — a scoped OBO token for that user.
  3. Backend reads the token and calls Statement Execution / Genie as the user.
  4. Unity Catalog applies that user's grants, masks, and row filters.
Program (REST API)
  1. Caller obtains their own Databricks token (per-user OAuth).
  2. Calls POST /api/query with Authorization: Bearer <token>.
  3. Backend uses that token on the same execution path as the UI.
  4. Same governance applies — masking and filtering are identical.

Components

Built from managed services, not custom code

Semantic layer

Unity Catalog Metric Views

Two governed views — mv_risk_behavior and mv_data_movement — define measures (high-risk event count, average risk score, egress volume) once in YAML, with joins declared in the definition. SQL, Genie, and dashboards all consume the same definitions.

Role: the headless semantic layer, native to Databricks and governed by Unity Catalog by construction.
Agent

Genie One (managed MCP)

The app calls /api/2.0/mcp/genie — workspace-wide, with no space and no table limit. A question returns a narrative answer, the tables and columns used, and a suggested SQL statement.

Role: new metric views become answerable the moment a user has access to them; every call runs under the user's identity.
Serving layer

Databricks App (FastAPI + React)

A data explorer, a Genie chat, a SQL runner with "copy as API call", and a query history. The UI's Run button and the public /api/query share one OBO execution module.

Role: the SQL a user sees in the UI behaves identically when copied out and called over the API.
Governance

ABAC policies + governed tags

Columns carry governed tags (e.g. data_classification=pii). A single schema-level policy masks every tagged column; another filters rows by sensitivity — automatically, including on future tables.

Role: governance follows the data classification, not a hand-maintained per-table rule set.
App store

Lakebase (Postgres)

Real-time query history and saved queries, served from managed Postgres at low latency.

Role: instant, per-user operational state that complements the authoritative — but lagging — system tables.
Audit

System tables

system.query.history and system.access.audit record who ran which statement, as which identity, with what result.

Role: because everything runs under OBO, the audit trail is attributed to real users with no extra plumbing.

Identity & execution

One execution path, guarded

The backend resolves identity in a fixed order and then never deviates from it: a browser OBO token, an API caller's bearer token. That token is passed verbatim to Statement Execution and to Genie, so Unity Catalog does the enforcing — the app does not re-implement access control.

Shared engine

UI & API converge

Both the Run button and /api/query call the same function. Results, row counts, and governance are guaranteed consistent between the two surfaces.

Safety

Read-only by default

The query endpoint accepts only read statements (SELECT / WITH / SHOW / DESCRIBE / EXPLAIN); anything that would modify data is rejected before execution.

Serverless

Statement Execution API

Queries run on a serverless SQL warehouse via the Statement Execution API, returning column schema and rows — bounded by a configurable row limit.

Governance · the crux

The same SQL, different people, different results

Governance is enforced by Unity Catalog at execution time, not by the application. OBO establishes who you are; ABAC and governed tags decide what you may see.

SELECT email, source_ip, risk_score FROM <schema>.fact_access_events …  ← both users run the exact same SQL

🛡️ Security analyst exempted principal

email → casey.johnson@northpeak.com
source_ip → 10.24.9.13  ·  restricted-asset rows → visible

Exempted by the policy's EXCEPT clause → sees plaintext and all rows.

👤 Regular engineer everyone else

email → ***masked***
source_ip → ***masked***  ·  restricted-asset rows → hidden

Column mask hides PII; row filter removes restricted-asset rows.

The persona is chosen by the policy's TO account users EXCEPT <principal> (an account group in production). A policy matches columns by governed tag — has_tag_value('data_classification','pii') for masking — so any newly-tagged column, on any table, is covered without editing the policy. The API path is bound by the exact same policies: copy the SQL out, call it with a token, and it is masked and filtered identically.

The agent

Genie, governed and un-capped

The app talks to the Genie One managed MCP server with the user's OBO token. A question flows through three calls, and the app surfaces the answer plus a runnable SQL statement.

  1. genie_ask — submit the question; returns a conversation id.
  2. genie_poll — poll until complete; returns a markdown answer, a deep link, and any query items.
  3. genie_get_query_result — fetch the full rows for a query the agent ran.
Why workspace-wide MCP

No curation ceiling

A curated Genie space caps at 30 tables and must be maintained by hand. The managed MCP endpoint has no space and no cap: any table or metric view a user is entitled to becomes answerable automatically — and it answers strictly within that user's Unity Catalog permissions.

Also kept: a curated space as a "certified" high-guidance path for the blessed metrics.

Operational store

Lakebase for what system tables can't do live

Real-time history

Query history

Every query run through the app is logged to Postgres immediately and shown in the user's history — without the ~10-minute lag of system tables.

Reusable

Saved queries

Users can save a Genie-suggested statement (or any query) and pull it back up later — per-user, low-latency app state that doesn't belong in system tables.

Data model & scenario

An insider data-exfiltration investigation

Roughly 340,000 synthetic engineering-activity events model a realistic security scenario. Six Platform-team engineers (two of them contractors) show a two-week spike of risky behavior — after-hours access to restricted repositories, clone/export actions, and large downloads to personal cloud and USB.

ObjectRowsWhat it holds
dim_employee500Engineers — team, role, level, contractor flag.
dim_asset200Repos / databases / datasets / services, with a sensitivity level.
fact_access_events200,000Access events with a per-event risk score, after-hours and external-IP flags.
fact_code_commits80,000Commits, including sensitive files touched and after-hours flag.
fact_data_downloads40,000Egress events — destination, bytes, flagged status.

The driving question — "which engineers showed high-risk behavior this week?" — resolves cleanly to those six, with a sharp drop-off to everyone else.

Walkthrough

What a user does

  1. Explore  Open the app and browse the tables and metric views you have access to, with column descriptions and governed tags.
  2. Ask Genie  Type "which engineers were high-risk this week"; Genie explains the tables, columns, and definitions and returns a suggested SQL statement.
  3. Run the SQL  Send it to the SQL runner and execute as yourself (OBO); the result footer shows it ran as you.
  4. Copy as an API call  Grab a curl or Python snippet and call /api/query directly with your own token — governance is identical.
  5. Switch persona  Re-run the same SQL as a regular engineer — PII is masked and restricted rows disappear.
  6. Review the audit  See the query attributed to the real user in system.query.history.

Delivery

One-command deploy, one-command verify

Deploy

Asset Bundle + bootstrap

A Databricks Asset Bundle deploys the App with its OBO scopes; a bootstrap script provisions the pieces the bundle doesn't — Lakebase, governed data, and the Genie space. The workspace host comes from the CLI profile, so the same project deploys anywhere.

Verify

Acceptance test

A single test run checks the data, ABAC governance, metric views, Genie, the app API under OBO, Lakebase, and the audit source — so a fresh deployment can be validated in one command.

Document

Runbooks

A deployment guide (prerequisites, configuration, audit queries, teardown) and a demo guide (the walkthrough and talk-track) ship with the project.
